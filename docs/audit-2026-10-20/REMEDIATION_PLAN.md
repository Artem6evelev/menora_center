# План исправлений Menorah Center

20 октября 2026. Основание: аудит `main@c43b0d5`, [AUDIT_REPORT](AUDIT_REPORT.md), [SPEC_COMPLIANCE](SPEC_COMPLIANCE.md), [SPEC_DECISIONS](SPEC_DECISIONS.md). Выполнение продуктовых исправлений, миграций, смены аккаунтов и production-релиза в аудит не входило.

Работы ниже разделены на небольшие изменения. Успешные диагностические probes подтверждают существующие дефекты; после исправлений нужны тесты ожидаемого безопасного поведения. Новый стек, очередь, Docker или замена сервисов не требуются по результатам этого аудита.

## Совместимый переход данных

1. **Инвентаризация, без записи.** Зафиксировать окружение, schema version и окно измерения; получить только агрегаты null/unknown, дубли email/регистраций, детей и состояния оплат. Уже доступны 175 профилей, 54 завершённых, 121 без статуса, 28 элементов детей в 15 профилях, 1 группа повторяющихся нормализованных email, 42 event registrations и 36 kids applications. По паре event/user фактических дублей сейчас нет, хотя constraint отсутствует. Эти числа относятся только к БД из локальной конфигурации.
2. **Старые значения.** «Еврей по материнской линии» — кандидат на соответствующий новый ответ, но не доказательство новой процедуры проверки. «Прошел гиюр» — кандидат на объединённый ответ, окончательные права зависят от D01/D02/D05. «Готовлюсь к Гиюру» не означает продвинутый этап. «Соблюдающий/Светский еврей», «Еврей по отцовской линии», «Интересуюсь иудаизмом», null и неизвестные не переводятся в разрешающий статус автоматически. Исходную строку сохранить. Пол не восстанавливать по косвенным данным.
3. **Расширение схемы.** Добавить новые поля/связи/исключения с nullable/unknown без разрешающих default; старые readers должны продолжать работать. Записать версию политики и источник данных, если модель утверждена. Не переименовывать/удалять прежние поля в том же релизе.
4. **Дети.** Сначала присвоить стабильные ID синтетическим/копированным записям в dry-run, сохранить legacy index и снимок исторического состава. Не переносить ребёнка другому родителю и не менять статус отца автоматически. Неоднозначные или старые связи остаются в отчёте ручной сверки. Число «детей отцов» неизвестно из-за отсутствия пола и подтверждённого родительства.
5. **История и деньги.** Сохранить все регистрации/платежные состояния/семейные связи до D06. `paid` в БД не доказывает оплату: есть обход суммы и unsigned webhook; нужна отдельная сверка с провайдером владельцем в разрешённой среде. Нельзя автоматически взыскать, отменить или вернуть деньги по результатам этого аудита.
6. **Пробный прогон.** Использовать обезличенную копию/синтетический seed; детерминированная таблица соответствий, versioned checkpoints, повторный запуск без дублей и изменений уже обработанных значений. Сравнить числа, FK, историю и возможности до/после. Пробный прогон миграции в текущем аудите не выполнялся.
7. **Сессии и кеш.** Определять пользователя из действующей сессии, права из актуального источника; version/TTL при кеше и явная инвалидизация при изменении прав. Сбросить scoped Zustand/localStorage intents при logout/account switch и после отказной ветки. Старый запрос после отзыва права должен отказать; очередь/отложенный callback повторно проверяет нужное право в момент действия. Финализацию уже принятого платежа отделить от разрешения на новую запись.
8. **Резервирование и откат.** До миграции проверить backup и восстановление на отдельной БД, сохранить mapping и schema-only snapshot. Откат кода допускается только к совместимой с расширенной схемой версии. Откат данных — отдельный план, без удаления новых регистраций/оплат; сначала stop write для затронутого пути и обратное преобразование по журналу, затем контроль агрегатов. Возвращение к открытому уязвимому коду не считается безопасным rollback.

## Решения владельца и независимые работы

До включения новой политики нужны D01–D10. Их отсутствие не мешает R01–R07, защите объектов, исправлению оплаты, подписи webhook, XSS, дублей, стабильных ID и подготовке тестов. Новая анкета может быть подготовлена на synthetic data, но права гиюра, переход старых пользователей и спорную маркировку отца нельзя выпустить на догадках.

Для оставшейся проверки нужны: deployment ID/commit и настройки проекта Vercel; тестовый Clerk tenant с Google и аккаунтами ролей; тестовая БД с воспроизводимой схемой/seed; sandbox контракт Shutafim; безопасные получатели Telegram/SMTP/WhatsApp; документы о backup/restore и согласованная таблица прав. Никакой отправки реальным посетителям для этих проверок не требуется.
