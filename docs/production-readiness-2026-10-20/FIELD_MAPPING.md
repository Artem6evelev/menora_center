# Поля анкеты и обратное чтение

Источник: текущая `components/dashboard/main/onboarding-form.tsx`; строгие контракты `lib/community/validation.ts`, транзакция `profile-write.ts`. Никаких дополнительных вопросов об email, документах или модерации не введено.

| Поле интерфейса | Серверная валидация / условие | PostgreSQL | Повторное чтение и карточка CRM |
|---|---|---|---|
| Связь с еврейством, ровно 3 ответа | `affiliation`: maternal / giyur / none | `users.affiliation`, nullable CHECK | `/register`, список/фильтр CRM и «Связь с еврейством» карточки |
| Пол, отдельное поле | `gender`: male / female, обязателен для сохранения | `users.gender`, nullable CHECK | Радиокнопки `/register`, «Пол» карточки |
| Уточнение гиюра | advanced / completed / null; только ветка giyur; для личной записи женщины не обязательно | `users.giyur_stage` | Анкета/однополевая форма детей, стадия в списке и карточке CRM; null не completed |
| Имя | trimmed 2–100, полные ветки | `users.first_name` | Анкета и список/карточка CRM |
| Фамилия | trimmed 2–100 | `users.last_name` | Анкета и список/карточка CRM |
| Номер телефона | строка 7–25 символов, разрешённые телефонные символы | `users.phone` | Анкета и карточка CRM |
| Дата рождения | существующая дата YYYY-MM-DD в прошлом | `users.date_of_birth` timestamptz, UTC midnight | Анкета date input, дата в CRM в Asia/Jerusalem |
| Город проживания | trimmed 1–150 | `users.city` | Анкета и карточка CRM |
| Семейное положение | single / married / divorced / widowed | `users.marital_status` | Анкета select, переведённое значение в карточке CRM |
| Имя супруга/и | обязательно только при married, max150 | `users.spouse_name` | Условный input и карточка CRM; другая семейная ветка сохраняет null |
| «Есть дети» | boolean; false не выводится из длины сохранённого массива | `users.has_children` | Checkbox и отдельный ответ Да/Нет/Не указано в карточке CRM |
| Имя каждого ребёнка | trimmed 2–100, максимум20; только разрешённая мама, принадлежность прежнего ID | `users.children_data[].name` | Анкета/кабинет детей и список детей в карточке CRM |
| Дата рождения каждого ребёнка | существующая дата в прошлом | `users.children_data[].dateOfBirth` | Те же три места; legacy birthDate читается совместимо |
| Добавление/удаление строк детей | strict array; ID/parentId нормализуются сервером, чужие ID отвергаются | `children_data[].id/parentId`, snapshots истории в существующих `event_participants.extra_data` | Устойчивый ID сохраняется после повторного чтения; история не меняет владельца |
| Согласие с политикой | literal true для полной отправки | `users.agreed_to_privacy` | CRM «Согласие с политикой»; повторная отправка требует явного checkbox |

Email не является вопросом актуальной формы: `users.email` получает email аккаунта из серверного `currentUser()` Clerk; карточка подписана «Email аккаунта Clerk». Владелец определяется стабильным Clerk ID, а не введённым адресом. Объединения адресов/Gmail нет. `source` — существующее необязательное поле старого серверного контракта, не новый вопрос: переданное значение сохраняется в `users.source`, отсутствие сохраняет прежнее, `""` явно очищает; в CRM показан «Источник (сохранённый)».

`filter_version=2`, `filter_completed_at`, `filter_revision`, `is_profile_complete`, роль, audit и связь черновика — служебные данные. Версию и дату устанавливает сервер после валидации; клиентские role/completion поля отвергаются. «Новый фильтр не пройден» — техническая отметка рядом с категорией, не четвёртый ответ.

Отсутствующий `childrenData` сохраняет существующих детей: скрытие блока при смене категории/пола/ответа «Есть дети» не удаляет семью. Явный допустимый `[]` в серверном контракте отличается от отсутствия поля и очищает актуальный список после сохранения snapshot истории; для изменения состава также остаётся кабинет детей. `hasChildren=false` сохраняется независимо от исторических детей. Нет массового backfill, смены старого `jewish_status` или присвоения статуса ребёнку.

Анонимная полная отправка сначала сохраняет весь валидированный payload в `community_registration_drafts.payload` (TTL30мин). UUID попытки в URL не содержит персональных данных; секретный nonce — HttpOnly/SameSite=Lax cookie, в БД только SHA256. После настоящей проверенной сессии: профиль + дети/snapshot + версия/дата + погашение черновика фиксируются одной транзакцией. У использованного черновика payload очищается; тот же callback не создаёт дубль, другой Clerk ID не может присвоить погашенный черновик. Это не распределённая транзакция Google/Clerk/PostgreSQL. До отправки формы произвольного автосохранения нет.

Доказательства: `evidence/production-results.json` проверяет все поля, false/[]/отсутствие/очистку, авторизованное обратное чтение CRM, ревизии, две попытки, rollback, повтор SQL и подписанные Svix callbacks на синтетической БД. `evidence/browser/results.json` отдельно указывает реальные браузерные проверки и используемую границу идентификации; mock identity не подтверждает Google OAuth.

Явное сохранение восстановленной анкеты уже прошедшего v2 аккаунта, включая none, атомарно погашает тот же draft. Другая identity его не присваивает. Проверка: production-results и browser/review-results.
