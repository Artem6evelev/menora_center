# Порядок выпуска и ручной SQL

Кандидат локальный, публикации и удалённой миграции не было. Текущая конфигурация указывает на Supabase **gwuzekpkfrkmgluzblty**, БД postgres, eu-central-1; назначение production/staging владельцем не подтверждено. Выбирать этот проект только после подтверждения, что именно он целевой.

1. Подтвердить целевой проект и доступную резервную копию/восстановление. Проверить закрытие внешних условий из REPORT (прежде всего секреты и OAuth). Backup не создавался агентом.
2. В Supabase → целевой проект → **SQL Editor → New query** вставить **всё содержимое одного [SUPABASE_MANUAL_MIGRATION.sql](SUPABASE_MANUAL_MIGRATION.sql)** и выполнить целиком. CLI, замена имён и сборка фрагментов не нужны. Все DDL в одной транзакции с lock timeout5с/statement timeout60с. Скрипт содержит итоговый SELECT `MENORA_FILTER_V2_SCHEMA_READY`, `target_filter_version=2`, число сохранённых пользователей и уже завершивших v2. Успех редактора должен быть без ERROR; сохранить итоговый результат без персональных данных.
3. При любой ошибке **не менять SQL и не повторять отдельные куски**. Прислать текст ошибки, имя объекта и выбранный project ref, без паролей/URL/профилей. Незавершённая транзакция откатывается; если редактор оставил сессию в failed transaction, выполнить его штатный rollback/перезапуск query, затем разбирать определение. Несовместимые типы/default/nullability/check/FK/индексы намеренно останавливают скрипт. Блокировка также означает остановку, а не разрешение снимать чужие lock.
4. После проверки результата и отдельного разрешения на публикацию выпустить совместимый код кандидата. **SQL сам код не публикует.** Build/start/deploy приложения миграции не запускают. В этом запуске push/deploy отсутствуют; `.github` workflows в рабочей копии не обнаружены, подключённая Git→Vercel автоматизация извне не проверена. Перед будущим push проверить её отдельно.
5. Проверить настоящий вход, v2-фильтр старого пользователя, полное обратное чтение анкеты уполномоченным администратором, итог `/dashboard/events`, ресурсы для none и отказы детских операций. Новые платные операции в этом кандидате отключены; публикация такого ограничения требует согласования владельца.

## Что делает SQL

На уже существующей семейной схеме приложения он проверяет базовые поля/данные, PK, уникальный Telegram index, FK детей и RLS; согласовывает отсутствующие эффекты0004–0005 с точным сравнением определений; добавляет `filter_completed_at`, `identity_disabled_at`, таблицу серверных черновиков с UNIQUE token hash/owner FK и ограничение v2-даты. Никакие business-строки/старые статусы/журналы не обновляются. Старая отметка версии1 не даёт v2-доступа. Повтор после новых ответов ничего не сбрасывает.

Проверены синтетические состояния: семейный baseline до0004, наличие0004+0005, частично созданные пустые новые таблицы, несовместимые определения, повтор после реального вызова сохранения анкеты. Это не универсальная установка на произвольную голую БД. При отсутствии базовой семейной схемы скрипт останавливается; пустая установка проверяется отдельно штатной native Drizzle-цепочкой0000–0007. Значения по умолчанию не означают прохождение фильтра.

Внешнее чтение обнаружило старый17-элементный `drizzle.__drizzle_migrations`, совпадающий с архивной цепочкой `supabase/migrations`; Supabase CLI ledger пуст. Эффект0004/5 есть, но записи канонической новой цепочки нет. Этот SQL **не создаёт фиктивные записи**. Нативный runner требует явный DATABASE_URL, не читает .env, до DDL отвергает чужую/неучтённую историю. Не запускать его поверх ручной внешней схемы: дальнейшая автоматизация требует отдельного проверенного согласования истории. Предыдущий `--apply-current-environment` удалён из исторического helper; актуальный внешний путь только owner-run SQL.

## Активация и восстановление

Обязательное повторное прохождение включается **при переключении на код FILTER_VERSION=2**, после SQL. Не использовать смешанный трафик старого разрешающего кода и v2: убрать старые workers/кэши в согласованном переключении, при необходимости краткое обслуживание. Старые вкладки при новом запросе проверяются по свежей БД; RSC страницы и actions защищены отдельно, private responses не кешируются, смена identity скрывает прежний интерфейс, возврат BFCache перегружает страницу.

При ошибке кода вернуть только совместимую v2-версию либо режим обслуживания. Откат к прежнему коду с допуском по версии1 восстановит обход и не является безопасным rollback. Не удалять новые колонки/таблицы, не обнулять даты/ответы и не восстанавливать старый snapshot поверх поступивших новых анкет. Резервная копия нужна для аварийного восстановления по отдельно подтверждённому плану, а не для автоматического отката бизнес-данных.

## Секреты и оплаты: внешние условия

`.env/.env.local` сняты только с Git index; физические локальные файлы сохранены. История/старые копии содержат прежние секреты. Владелец должен отозвать/ротировать DB credential, Supabase privileged key, Clerk secret/webhook secret, SMTP, Telegram и cron secrets по фактическому перечню своего хранилища, передать новые значения через env-хранилище и согласовать очистку истории/копий. До доказательств ротации A01/R01 остаётся открытым; значения здесь не публикуются.

Shutafim iframe сохранён в исходниках; `PAYMENTS_RESTRICTED=true` не включается случайным env. Webhook отвечает503 без парсинга/финансовых изменений. Бесплатные новые записи — `confirmed`, прежние `paid` неизменны и в режиме только чтения. Для последующего этапа потребуется документированный контракт провайдера и проверка заказа/суммы/валюты/транзакции/повтора, затем отдельные тесты и разрешение на включение.

Сверка старых `paid`: уполномоченный оператор в закрытой среде сопоставляет существующий participant ID/event/user, время, ожидаемые суммы по сохранённым ценам/семье и фактический реестр Shutafim по transaction/order ID. Если в приложении нет сохранённого provider transaction ID, сам статус `paid` не доказывает оплату: строка остаётся «требует сверки». Фиксировать результат/основание/исполнителя в отдельном защищённом реестре, не выгружать контакты в чат. Не пересчитывать историю по сегодняшней цене, не выполнять UPDATE/DELETE или массовый сброс. Сверка и получение реестра в этом запуске не выполнялись.
