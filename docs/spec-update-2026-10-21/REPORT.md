## Решение по пункту 5 и сохранность детей

`/dashboard/kids` — отдельный детский сценарий. Кнопка «Добавить или записать ребёнка» открывает имеющийся короткий вопрос стадии для женщины из категории гиюра. Ответ сохраняется существующим `saveGiyurStage`, доступным до выдачи детских прав. После `advanced` действия остаются закрытыми; после `completed` свежая серверная политика разрешает операции при остальных условиях. Из события туда ведёт контекстная ссылка, обратно есть безопасная ссылка к событию. В основную анкету вопрос не возвращён. Мужчинам этот механизм прав не выдаёт.

Имена, ID, дата, пол проходят серверную проверку. Новый ребёнок требует явного пола. Старый неизвестный пол допустим; принадлежность проверяется по профилю текущего Clerk ID. Стадия в основной анкете не меняет сохранённое значение. Дети хранятся в существующем JSONB; перед изменением актуального списка прежние позиционные ссылки в билетах превращаются в исторические снимки. Изменение/удаление текущей записи не удаляет оплаченный билет, заявки или историю. Материнская категория/стадия не назначается ребёнку.

При сохранении ребёнка основной ввод временно блокируется; отложенный автосейв не записывает старый список поверх ручного сохранения. Ошибка не создаёт компактную успешную запись; возможен повтор. Перед OAuth автосохранение останавливается, чтобы не понизить готовую анкету до незавершённого черновика во время навигации. Восстановление проверяет cookie, владельца, срок и исходную цель; устаревшая sessionStorage-ссылка не меняет событие. URL и sessionStorage содержат только ID попытки/маршрут, без персональных данных.

## База данных и SQL

**SQL нужен только для `public.users.city_id text NULL`.** Пол ребёнка размещён в существующем `children_data JSONB`, отдельная колонка/таблица не нужна. Добавлена локальная Drizzle-миграция [0008_city_identity.sql](../../drizzle/0008_city_identity.sql) со snapshot/journal для канонической цепочки.

Для владельца подготовлен **один готовый блок** [MANUAL_SQL.sql](MANUAL_SQL.sql): проверка базовых таблиц и типов, совместимости `city_id`, `ADD COLUMN IF NOT EXISTS`, проверка результата, транзакция. Повторный запуск проверен; при несовместимой схеме блок отказывается продолжать. Не обновляет строки людей, пол детей, статусы, семейные данные, фильтр или журнал миграций. Перед публикацией кода нужно применить этот блок к подтверждённому владельцем проекту после backup.

В настроенной внешней Supabase выполнено только чтение схемы/журнала: [remote-schema-readonly.json](evidence/remote-schema-readonly.json). `city_id` отсутствовал; JSONB детей и предыдущие поля/таблица черновиков присутствуют. В журнале 17 записей, хеши локальных 0004–0007 не совпадают с ними. Поэтому отсутствие журнальной записи не трактуется как разрешение повторно применить эти миграции; `npm run db:migrate` к удалённой БД не запускался. Назначение внешнего проекта как production/test не предполагается. Все записывающие проверки — PGlite; браузерный стенд отказывается делать reset без подтверждения `isolated-pglite`.
