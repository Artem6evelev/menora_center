# Миграции и согласование внешней БД

## Действующий процесс в рабочем дереве

Каноническая цепочка — `drizzle/0000…0006` и `drizzle/meta/_journal.json`, схема — `lib/db/schema.ts`. `drizzle.config.ts` указывает именно `drizzle/`. Старый каталог `supabase/migrations/0000…0016` также имеет формат **Drizzle**, включая свой `meta/_journal.json`; это не вторая последовательность, которую следует выполнить после первой. Корневого migration script прежде не было. `drizzle-kit push` не является воспроизводимым применением этой цепочки.

- `npm run db:generate -- --name=<name>` — генерация средствами установленного drizzle-kit 0.31.10.
- `npm run db:migrate` — `scripts/migrate.cjs`, штатный `drizzle-orm/postgres-js/migrator` 0.45.1. Нужен явно переданный `DATABASE_URL`; env-файлы проекта автоматически не читаются. Значения не логируются.
- Перед DDL runner читает журнал и проверяет последовательность `created_at`/SHA256. Чужая история, изменённый checksum или существующие public-таблицы без канонического журнала приводят к отказу. Автоматического adoption/backfill нет.
- `npm run db:test` — та же цепочка через штатный `drizzle-orm/pglite/migrator`, с тем же PostgreSQL PgDialect/форматом журнала, на изолированном PGlite 0.5.10. Это PostgreSQL/WASM; отдельный нативный PostgreSQL server и Supabase Auth/Storage этим тестом не проверяются.

В `0004` добавлены statement-breakpoints между отдельными командами. Прежний блок из четырёх ALTER не принимался подготовленным запросом PGlite; в конце были также объединены ALTER/REVOKE. SQL-смысл сохранён, что проверяется сравнением нормализованного содержимого с [предыдущим файлом](evidence/0004-before-native-fix.sql). SHA0004 изменился с `34124c4a9c89a348323b834556d45e41c7d2d2f1364c1e96e9f9a27b99f3a7bb` на `cef39399cddcc59ac5654848d0ccfeee1be7c3fc3b1ed531a96f55c2b75130c7`. Preflight принимает оба эквивалентных checksum для уже зарегистрированной позиции 0004. `0005` не менялась.

Новая `0006_reconcile_existing_schema` восполняет исторический разрыв между `0003` и ORM: 14 колонок, `kids_applications`, её FK и unique index Telegram. Только отсутствующие колонки/таблица добавляются; существующие значения, статусы, JSON и оплаты не переписываются. Эквивалентный существующий FK распознаётся по структуре, даже если называется иначе. Несовместимые определения требуют отдельного согласования; IF NOT EXISTS не является доказательством их совместимости. RLS включён у всех 17 таблиц и отражён в ORM; публичные разрешающие политики не добавлены. Серверный owner-доступ сохранён, клиентский доступ к этим таблицам не открывается.

`db:generate` после изменений сообщает `No schema changes, nothing to migrate`. Миграции не запускаются при build/start/deploy автоматически.

## Результаты изолированного воспроизведения

[Полный протокол](evidence/migration-results.json), [лог](evidence/migrations-followup.log): **8/8 PASS**.

1. На пустой БД нативно применены все 7 миграций. Колонки, типы, nullability, defaults, PK/unique/FK/CHECK, индексы и RLS совпали со схемой, независимо сгенерированной из текущей ORM.
2. В журнале появились 7 настоящих записей hash/created_at, в том числе 0004/0005/0006. Подставленных записей нет.
3. Повторный native migrate не выполняет migration statements; журнал и схема неизменны.
4. Для upgrade сначала native migrate создал 0000–0003, затем синтетически воспроизведены ранее существовавшие семейные/payment-поля и таблица заявок. До 0004 загружены старые дети, супруг, подтверждённая детская заявка, оплаченные event/service-записи, опубликованный контент и объединённый гиюр-ответ.
5. Native upgrade0004–0006 сохраняет fingerprints всех прежних бизнес-строк и связей. Неизвестные gender/affiliation/giyurStage/filterVersion остаются NULL, filterRevision получает 0. Публикации/оплаты не сбрасываются.
6. Иное прежнее имя FK не создаёт дублирующую связь.
7. Повторный upgrade — no-op; проверены отказы preflight для чужого журнала, неизвестного baseline и изменённого hash.
8. Уже зарегистрированная 0004 v1 совместима; семантическая эквивалентность v1/v2 проверена.

## Что установлено о внешней среде

Только READ ONLY: Supabase **`gwuzekpkfrkmgluzblty`**, database `postgres`, локальные env используют этот проект; production/staging назначение не установлено. [Новые metadata и журналы](evidence/database-followup-readonly.json).

Все 17 строк `drizzle.__drizzle_migrations` по SHA совпали с **`supabase/migrations/0000…0016`**. `supabase_migrations.schema_migrations` пуст. Эффект 0004/0005 уже есть, записей нет. Причина известна: предыдущая разрешённая точечная починка `tests/community/check-environment.cjs --apply-current-environment` исполняла SQL напрямую без migration journal. [Старый протокол](../evidence/environment-schema-repair.json) фиксирует первоначальные SHA и неизменность бизнес-строк. В этом запуске этот флаг не использовался.

Новый 0006 на внешнюю БД не применён. Исторические 0000–0003 не переписывались. Существуют дополнительные расхождения: `videos.created_at` в БД — timestamp with time zone, в ORM — без timezone; дополнительная `bot_settings.admin_notification_chat_id`; отсутствуют FK `news.author_id → users.id` и `news_comments.user_id → users.id`. Другие имена эквивалентных FK/unique не считаются отсутствием связи. Все 17 таблиц имеют RLS. Эти находки не закрыты локальным тестом.

## Конкретный план согласования без исполнения

1. Владелец инфраструктуры определяет назначение project ref и разрешённое окно изменений. До этого — только чтение. Создать проверенный backup schema+data+всех ledger, сохранить recovery point и восстановить **изолированную копию**. Персональные данные из копии не публиковать и не использовать в UI-доказательствах.
2. На копии сверить полные определения колонок/defaults/nullability, CHECK, FK/delete actions, unique indexes, RLS/policies/ACL с 0006 snapshot. Сопоставлять семантику, не только имена. До создания unique проверить duplicate Telegram IDs; до FK — orphan author/user IDs. При расхождении остановиться, данные не удалять и не исправлять предположением.
3. На копии подготовить отдельный reviewed reconciliation artifact: сохранить дополнительную bot-колонку; сохранить значения `videos.created_at` и явно согласовать timezone/ORM mapping; для отсутствующих FK сначала решить orphan cases и validate constraints. Не выполнять cast времени с неустановленным timezone и не переписывать публикации/оплаты. Fingerprints детей, семей, записей и оплат должны остаться прежними.
4. Выбрать **явный adoption baseline** для канонической цепочки. Прежний журнал 17 строк сохранить под архивным именем/в отдельной schema вместе с backup. Зафиксировать mapping «старый SHA → фактический эффект → соответствие новому baseline» и отдельно прямое выполнение 0004 v1/0005. Не выдавать root0000–0003 за реально выполненный SQL и не добавлять их без baseline-протокола. Для существующей БД создать согласованный baseline/отдельный ledger, который документирует adoption, а не фиктивное исполнение. В текущем runner adoption намеренно отсутствует: его формат/guard следует добавить только после проверки конкретного baseline на копии.
5. Проверить на копии: первый migration run выполняет только ещё отсутствующий reviewed delta; baseline/ledger соответствуют схеме; второй native run — no-op. Повторить все 8 migration checks и целевые 26/12/11 tests; сверить бизнес-fingerprints и rollback/recovery.
6. Лишь после review конкретного SQL/ledger artifact и разрешения изменений в установленной среде выполнить согласованный adoption. Текущая задача **не разрешает** автоматически выполнять этот план на неизвестной внешней БД. До такого согласования новый runner корректно отвергает её смешанную историю.

Основание процесса: [Drizzle migrations](https://orm.drizzle.team/docs/migrations) и проверенный исходный код установленного мигратора. Перенос на Supabase CLI-историю в этом этапе не выполнялся.
