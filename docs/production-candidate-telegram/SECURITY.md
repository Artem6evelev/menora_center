# Проверка затронутого контура

Доказательства: [все результаты](evidence/checks.json), [native PostgreSQL](evidence/telegram-native-results.json), [PGlite](evidence/telegram-release-results.json), [граница client/server](evidence/client-boundary.json). Это целевая проверка Telegram/Mini App/CRM/handoff, не повтор общего аудита сайта.

- InitData: исходная HMAC-проверка всех подписанных полей, freshness/future skew и branded bootstrap proof сохранены. Resume связывает подпись Telegram subject с действующей собственной cookie; старый launch не выпускает новую сессию. Токен только HttpOnly cookie, SHA-256 в БД, expiry/revocation/disabled identity проверяются сервером.
- Изменения Mini App: same-origin, bounded JSON, strict schemas; cookie определяет canonical user. Filter/profile сохраняют прежние ETag/revision и общую policy. События требуют актуальной полной анкеты; третья категория не получает event data. `audience` остаётся прежним полем интерфейсного фильтра сайта, новых бизнес-ограничений по полу не введено.
- Семья: сервер сам загружает собственных детей. Мужчины не записывают детей. Женщина giyur unknown/advanced записывает только себя, completed допускает детей. Отдельное уточнение находится в child action; в основную анкету стадия не возвращена. Общие website/admin child rules и сохранение истории проверены.
- Цены: общий calculator использует точные целые агороты из DB prices; неверный формат цены и подставленные client total/user/chat ID отвергаются. Paid attempt хранит immutable сумму, selection hash, URL и registration reference. Повтор возвращает ту же попытку; иной состав в уже переданной попытке не перезаписывает её. Website legacy iframe без такой попытки сохраняет прежний пересчёт; попытка Mini App защищена и от записи через website handler.
- Оплата: free → confirmed, paid handoff → pending. Нет нового способа установить paid/confirmed через закрытие, return URL или произвольный webhook. Существующая блокировка непроверенного подтверждения оплаты сохранена.
- Bot: constant-time сравнение webhook secret до JSON/DB; update ID фиксируется атомарно с bootstrap/изменением состояния. Replay проверяется до создания личности, включая повтор ID с изменённым subject. Private chat/user IDs должны совпасть. Старый holiday flow и fake-email writer удалены. Mini App/bot одновременно используют одну identity-архитектуру; native pool подтвердил конкурентный bootstrap.
- HTML: единый escaping helper для динамических имён/названий в HTML; CRM broadcast — plain text, без parse_mode. Служебные уведомления больше не экспортируются публичными server actions; это `server-only` helper вызывающих серверных обработчиков.
- CRM: requireStaff/current filter на каждом action, роль повторно проверяется внутри enqueue transaction. Только canonical IDs и первичный Telegram contact; произвольный chat ID не принимается. Все filtered recipients вычисляются на сервере, а не по текущей странице. UI получает 20 строк; enqueue максимум 5000, DB insert порциями 250.
- Queue: только явный opt-in, известный private chat, отсутствие block/disabled user. Повторная проверка перед HTTP; unsubscribe после enqueue исключает доставку. Глобальная advisory-lock claim и один sending исключают одновременную отправку, межзапросный интервал минимум 80 ms. До 5 deliveries за invocation, budget цикла24 s плюс завершающий HTTP timeout5 s, maxDuration30. Отдельный route требует непустой CRON_SECRET; `Bearer undefined` отвергается. Ручной drain требует staff.
- Retry: Telegram JSON `ok:false` 429 → retry_after и общий cooldown; определённый 5xx → bounded exponential backoff; максимум 5 попыток; 403 → blocked; permanent400 → failed. Неопределённый network/response outcome → unknown, не auto retry. Зависший sending через 120 s → unknown. Это предотвращает повтор сообщения после возможной доставки; exactly-once гарантии Telegram Bot API нет. Unknown требует проверки оператором, не сброса в queued вслепую.
- Consent: /start, launch и link не подписывают. Opt-in/out timestamps сохраняются. Валидное будущее interaction снимает transport block в unknown, не возвращает marketing opt-in автоматически. Webhook welcome отправляется один раз на update; после сбоя ответа пользователь может вызвать новый /start, replay старого не переотправляет.
- Campaign: только opaque keys, first_start_param не перезаписывается; last/seen обновляются. Server mapping `telegram_campaigns` не выдаёт доступ к событию. Bot передаёт campaign marker в кнопку, UI разрешает mapping на сервере после фильтра. PII в campaign keys запрещена операционным контрактом; нельзя использовать email/телефон/имя как ключ.
- БД: пять operational tables с RLS, без public policies и effective table/column grants PUBLIC/anon/authenticated; FK/unique/check ограничения, atomic refusal несовместимой частичной схемы. Индексы под event list, owner/event и queue due queries. Unified SQL повторён на PostgreSQL17.5/18 PGlite и native18 с сохранением paid history/children/consent. Удалённая Supabase не читалась.
- Логи: только фиксированный event/error class и числовые counts/amount. Нет initData, session/bot/webhook secrets, raw update, семейных payload, email/phone. Static client chunks проверены на server-only markers. Загружаемый JS Mini App не содержит Clerk runtime.

Ограничения доказательств: реальные Telegram WebView/доставка/429 от настоящего Telegram и подтверждение Shutafim не выполнялись. Native тесты используют настоящий PostgreSQL/postgres-js и независимые connections, но Bot API остаётся stub; browser identity/SDK синтетические и не являются Google/Telegram OAuth acceptance.
